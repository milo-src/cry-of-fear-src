# Серверная музыка: адресат stop, сохранение состояния, vtable

Статический разбор оригинального `hl.dll`, SHA-256
`751a68831e4fe3541bbbb24da3c785fb9f6cd3d7e6dcd92125fe1e18f0fce641`.
Новые доказательства: [raw bytes и метаданные](music-server-state-evidence.json),
[воспроизводимый ограниченный PE/objdump сборщик](music-server-state-capture.py).
Двоичный модуль не загружался и не исполнялся, новая REA-сессия не создавалась.
Все диапазоны в JSON имеют исключительную верхнюю границу, file offset,
байты и SHA-256; каждый asm имеет отдельный SHA-256 и полную команду objdump.

Этот проход закрывает три прежних вопроса из
[music-server-protocol.md](music-server-protocol.md). Прочие выводы того разбора
остаются в силе: одна перезаписываемая запись, не FIFO; fade сущности берётся
из native `pev.frags+168`, не health.

## Оба stop имеют того же адресата, что и play

В PostThink `100ead70` подготовка четырёх аргументов MessageBegin общая для
stop/play и находится **до** условного перехода по `player+2310`.
Ghidra C потерял аргументы именно на stop-ветках, а не сам вызов.

| Участок | Подготовка | Stop call | Play call | Очистка pending |
|---|---|---|---|---|
| Первый | `100eb84e..100eb860` | `100eb864` | `100eb8b0` | `100eb90d` |
| Второй | `100ef0c4..100ef0d6` | `100ef0da` | `100ef129` | `100ef186` |

В обоих случаях стек вызова соответствует
`MessageBegin(1, [10226544], 0, [[player+4]+20c])`:
`MSG_ONE`, зарегистрированный `PlayMP3`, нулевой origin, конкретный
`player.pev.pContainingEntity`. Идентификация engine callback slots уже
подтверждена `analysis/abi/GiveFnptrsToDll.asm` и `enginefuncs_t`;
новые asm доказывают сами аргументы. Это не broadcast и не MSG_ALL.

Stop wire: `BYTE 0`, `BYTE 0`, `COORD [player+2318]`, `STRING "nothing"`, End.
После отправки `+2318=0`, затем `+2314=0`. Play wire остаётся
`BYTE bool(+231c)`, `BYTE 1`, `COORD +2320`, `STRING(stringBase + +2310)`;
после него очищается только pending из этих полей. Оба участка сначала
проверяют `+2314!=0`, а затем текущий path. Уже разобранные outer gates и
возможные промежуточные постановщики запроса здесь не изменяются.

Доказательства: [первый участок](music-server-state-stop-early.asm),
[второй участок](music-server-state-stop-late.asm), полный сохранённый
`decompiled/server/partial-pass/functions/0x100ead70.c`.

## Что входит в PLAYER save fields

`Save100f1940` после успешного `100c1ec0` вызывает `1011adc0` с объектом,
таблицей **10217fe8**, количеством **207 (0xcf)** и строками `cPLAYER`/`PLAYER`.
`Restore100f14c0` после успешного `100c19a0` вызывает `10117010` с тем же
объектом, `PLAYER`, таблицей и количеством. Байты строк сохранены отдельно.
В evidence есть **вся таблица 207×16 байт**, а не только четыре выбранных
записи. Layout записи: type DWORD, name VA DWORD, object offset DWORD,
count WORD, flags WORD. Все четыре записи имеют count=1, flags=0.

| Index / VA записи | Native name | Player offset | Type ID | Размер из native size table |
|---|---|---|---|---|
| 43 / `10218298` | `m_strCurrentMp3` | `2310` | 1 | 4 |
| 47 / `102182d8` | `m_fMp3FadeTime` | `2318` | 0 | 4 |
| 48 / `102182e8` | `m_bMp3ShouldLoop` | `231c` | 12 | 4 |
| 49 / `102182f8` | `m_fMp3FadeInTime` | `2320` | 0 | 4 |

**Pending `+2314` отсутствует среди всех 207 offsets этой PLAYER-таблицы.**
Это ограниченное утверждение о данной таблице; оно не доказывает отсутствие
какого-либо другого механизма сохранения во всей DLL.

Типы сверены с уже сохранёнными helpers, а не только с SDK enum:
`1011adc0` для type0 вызывает float writer `1011b110`, для type1 —
`1011b320`, для type12 — `1011b190` с размером `count*4`.
Native size table `1021b140` также содержит 4 для каждого из этих типов.
То, что wire/queue употребляет bool в младшем байте `+231c`, не означает
однобайтовое поле сохранения: native serializer обрабатывает четыре байта.

`1011b320` получает текст через `stringBase + storedOffset`, пишет длину и
строку с завершающим NUL. `10116c50` при чтении type1 для непустого текста
вызывает engine slot `10223054` (AllocString); пустая строка даёт offset0.
Таким образом сохраняется содержимое path, а не переносимый raw VA.
Точная внешняя структура save-файла и остальные типы не являются целью
этого прохода. `10116420` распознаёт полностью нулевое поле; save writer
пропускает такие записи. Reader `10117010` предварительно обнуляет поля
таблицы согласно их count/type size и flags, затем читает присутствующие.

## После restore трек получает новый запрос

В [Restore asm](music-server-state-restore.asm) по `100f176e` читается
`player+2310`, по `100f1776` ноль пропускает вызов. Иначе по `100f1785`
вызывается **QueueMusic100ea5c0(path, 1, 1.0f)**. Следовательно:

- Сохранённый path восстанавливается, а loop и playFade затем принудительно
  заменяются на 1 и 1.0. Это не буквальный повтор сохранённых loop/fade.
- QueueMusic устанавливает pending=1; следующий доступный sender PostThink
  доставляет play. Наличие pending в save-таблице для этого не требуется.
- StopFade `+2318` сериализуется, но данный requeue его не очищает.
- При path0 эта ветка не вызывает QueueStop и не создаёт stop-сообщение.
  Самостоятельное состояние pending и иные lifecycle-пути при path0 этим
  фактом не исчерпываются. Позиция воспроизведения/декодер внешнего audio backend среди этих
  четырёх полей не представлены.

Save дополнительно обнуляет `player+4c8` после writer; музыкальный разбор
не приписывает этому полю новый смысл. Большая остальная часть Restore
(геометрия, physics keys, health) остаётся описана прежними отдельными
контрактами и не объявляется полностью раскрытой.

## Фабрика → vtable → Use теперь числовая связь

`101084f0` использует существующий private data, если он найден; на ветке
создания запрашивает `0xdc` байт. По **10108538** инструкция с байтами
`c7 00 38 44 1e 10` пишет **101e4438** в первый DWORD объекта.
Следующая инструкция записывает entvars в `object+4`.

Raw DWORD по **101e4520 = 101e4438+e8** равен **101148b0**:
это именно ранее разобранный `CAmbientFmodStream_Use` / рабочее семейство
`CTriggerMP3`, а не предположение по соседним именам.
Контрольные slots: `+2c -> 1000e220`, `+34 -> 1000dba0`; их полный смысл
здесь отдельно не исследован.

Три export-thunk E9 rel32 также сохранены raw и каждый вычисляется в
`101084f0`: `ambient_fmodstream10115c80`, `trigger_mp310115f20`,
`trigger_mp3audio10115f30`. [Factory asm](music-server-state-factory.asm)
и raw slots замыкают связь exported classname → factory → Use.
Имена классов остаются рабочими обозначениями; числовая связь от них
не зависит. Семантика Use, его MP gate и remove flags не пересматривались.

## Границы

Три конкретных server-вопроса закрыты статическими байтами. Этот результат
не равен runtime-проверке музыки, полному разбору Save/Restore/PostThink
или доказательству точного playback cursor после загрузки. Клиентская
обработка fade, состояние внешнего audio backend (клиентский irrKlang) и маршруты иных audio senders описываются
отдельными контрактами; новым захватом сервера не подменяются.
