# Границы клиентского декодирования STRING и COORD

Статический аудит уже сохранённых артефактов client.dll, SHA256
`e0d0ef0eac981bda321c834e7d73ad7a905cc66bcbed13706bc8e24eac284360`.
Дата: 2026-11-20. В этом подзадании REA, игра и сборка не запускались. Документ
связывает [оригинальные WRITE_STRING/WRITE_COORD](engine-wire-contract.md) и
[staging/MessageEnd](engine-message-buffer-contract.md) с доказанным приёмом
PlayMP3 и custom texture messages. Он не утверждает безопасность всех входов.

## Слои, которые нельзя смешивать

```text
server source string / duration
  -> original engine writer и user-message framing
  -> callback(buffer, size)
  -> InitReader / ReadByte / ReadShort / ReadCoord / ReadString
  -> strncpy(..., 256)
  -> музыкальные методы или texture path / ready flags
```

Предел scratch ReadString равен 2047 полезным байтам; следующий destination
имеет размер 256 байт. Ни один из этих фактов не определяет автоматически
максимальный размер сетевого user-message. Поведение writer при null,
переполнении и преобразовании float определяется оригинальным engine отдельно.
Серверный вызов WRITE_STRING(NULL) нельзя вывести только из client empty-string
ветки как передачу нулевого байта, хотя такой приём согласуется со сбросом пути.

## Общее состояние reader и владение результатом

InitReader 10080850 сохраняет четыре глобальных значения:

| Адрес | Значение |
|---|---|
|105440b4|Исходный указатель buffer|
|105440b8|Размер buffer, переданный callback|
|105440bc|Текущий cursor, сбрасывается в 0|
|105440c0|Bad-read state, сбрасывается в 0|
|105440c8|Начало общего scratch ReadString, вместимость 2048 байт|

Это globals reader, а не поля одноимённых смещений звукового контекста a4.
InitReader не копирует входные данные и не проверяет pointer/size. ReadString
возвращает один общий scratch; следующий вызов перезаписывает его начало.
В рассматриваемых handlers результат сразу копируется в отдельный destination.
Владение исходным packet остаётся у вызывающего слоя. Общие globals не дают
гарантии независимых вложенных или параллельных reader-сессий.

Ниже обычные границы предполагают неотрицательный размер, валидный buffer и
cursor в пределах размера. Тело не доказывает безопасность отрицательного size,
арифметического переполнения cursor+1/+2 или некорректного указателя.

## Примитивные readers

| Функция | Успешное чтение | Не хватает данных |
|---|---|---|
|100808b0, ReadByte|Unsigned byte 0..255; cursor +=1|Возвращает 0xffffffff, bad=1, cursor прежний|
|100808e0, ReadChar|Signed byte -128..127; cursor +=1|Возвращает -1, bad=1, cursor прежний|
|10080a10, ReadShort|Signed16 little-endian; cursor +=2|Возвращает -1, bad=1, cursor прежний|
|10080910, ReadCoord|ReadShort() ×0.125|Тоже умножает возвращённый -1, результат -0.125|

ReadShort проверяет наличие обоих байтов до чтения. При одном оставшемся байте
он не потребляет этот байт: последующий reader может прочитать его как другое
поле. Bad-read не блокирует дальнейшие reads и не очищается при успешном read;
он сохраняется до нового InitReader. ReadCoord не проверяет этот state.

При валидном signed16 диапазон принятого COORD: -4096..4095.875 с шагом 0.125.
Код 0xffff законно декодируется в -0.125, то есть совпадает с числовым результатом
ошибки короткого чтения. Различить их можно по состоянию/cursor, но не по одному
float. Округление и переполнение **encoder** из этих формул не следуют.

## ReadString 10080a60: точные условия остановки

Функция сохраняет локальный snapshot size, обнуляет scratch[0] и проверяет
`cursor+1 <= snapshot_size` перед каждой попыткой. Затем вызывает ReadChar,
который самостоятельно проверяет глобальный size. Результаты 0 и -1 завершают
строку без копирования; остальные signed значения копируются обратно как char.
После каждого записанного байта увеличивается index; при index>0x7fe цикл
останавливается. Затем записывается scratch[index]=0.

Предел полезного результата — **2047 байт**, завершающий NUL — scratch[2047].
Установленная rangecheck-ветка при index>=2048 не является обычной сигнализацией
усечения: нормальный цикл уже заканчивается на 2047.

| Причина остановки | Какие байты потреблены | Выходная строка | Bad-read |
|---|---|---|---|
|Входной NUL 0x00|Предшествующие байты и сам NUL|NUL не копируется, свой NUL записывается в scratch|Не устанавливается|
|Входной 0xff|Предшествующие байты и сам 0xff|0xff не копируется, свой NUL записывается|Не устанавливается: ReadChar успешно вернул signed -1|
|Достигнут size до нового read|Только доступные предшествующие байты|Свой NUL добавляется даже без входного терминатора|Не устанавливается: неуспешный ReadChar не вызывается|
|Скопированы 2047 байт|Ровно эти 2047; следующий байт не читается|Свой NUL в позиции 2047|Не устанавливается|
|ReadChar вернул -1 из-за нехватки|Неуспешный read cursor не сдвигает|Свой NUL после уже скопированного|ReadChar ставит 1; при неизменном корректном size обычная предварительная проверка предотвращает этот случай|

Байты 0x80..0xfe сохраняются как исходные байты, хотя промежуточное число signed.
Это не UTF-8/Unicode decoder. Только 0xff из верхнего диапазона равен sentinel -1.
Состояние bad, уже установленное предыдущим полем, ReadString не очищает.

При cap2047 функция **не ищет и не пропускает остаток до NUL**. Например, для
2047 ненулевых байтов и следующего NUL cursor останется перед этим NUL; следующий
ReadString вернёт пустую строку и потребит его. При 2048 ненулевых байтах следующий
reader начнёт с 2048-го байта. В рассматриваемых messages STRING является
последним полем, поэтому из этого нельзя делать вывод о смещении уже прочитанных
предшествующих полей; это ограничение для будущего воспроизведения общего reader.

## Переход scratch → 256 байт

PlayMP3 10070ee0 и три custom readers используют `_strncpy(dst, scratch, 256)`
без отдельной записи `dst[255]=0`. Следствия стандартной семантики обнаруженного
strncpy-вызова, согласующиеся с существующим аудитом:

| Длина декодированной строки L до NUL | Результат strncpy256 |
|---|---|
|0..255|NUL находится внутри destination; короткий остаток дополняется нулями|
|256..2047|Копируются первые 256 ненулевых байтов; NUL в destination не гарантирован|

Строка длиной ровно 256 уже попадает во вторую категорию, даже если её source
корректно заканчивается NUL. Cap2047 не заменяет cap255 для такого назначения.
Найденный strncpy здесь не исследован заново на уровне CRT SIMD-реализации;
данный аудит проверяет call sites и отсутствие дополнительных ограничений.

### PlayMP3

10070ee0 читает BYTE loop, BYTE play, COORD duration, затем STRING в scratch и
копирует его в локальный stack buffer[256]. При cvar cl_downwiththesickness==1
переписывает весь destination через strncpy256 коротким фиксированным именем;
только эта ветка сама гарантирует короткую строку независимо от прочитанного имени.

Handler не проверяет bad-read. Ненулевой play выбирает запуск; ненулевой loop
становится true. Возвращённый при ошибке byte 0xffffffff тоже ненулевой.
Строка копируется даже в stop-ветке, однако там не передаётся музыкальному producer.
При play локальный buffer идёт в 1007faf0 →1007fd50, где есть строковые сравнения
и копирование без видимого общего ограничения длины. Поэтому отсутствие NUL
не исправляется автоматически этим переходом.

Если +c4 контекста активен, 1007fd50 сохраняет **адрес этого локального buffer**
в +c8 и выходит. Nonzero writer +c4 пока не доказан; это условная цепочка
данных, не утверждение о достижимом повреждении памяти. После возврата handler
такая запись сама по себе не обеспечивает время жизни строки. Scratch reader
и stack buffer — два разных временных хранилища, ни одно не становится owning
allocation только из-за сохранения указателя.

### CustomFng / CustomGlv / CustomSlv

| Handler | Destination | Действия после копирования |
|---|---|---|
|1006fb40|HUD+11c =1018a1dc|active10542bb0=1; NUL scan; длина<3 очищает path/active; ready104d26c7=0|
|1006fbb0|HUD+21c =1018a2dc|active10542bb1=1; NUL scan; длина<3 очищает path/active; ready104d26d0=0|
|1006fc20|HUD+1c =1018a0dc|NUL scan; длина<3 очищает path; ready104d26c6/d3=0|

Scan не ограничен 256 байтами. При L>=256 destination не гарантирует терминатор
внутри поля; следующий scan не имеет локально доказанного предела. Проверка
«длина<3» идёт **после** scan и не защищает верхнюю границу. Эти функции не
отвергают сообщение по bad-read и не требуют наличия входного NUL. Пустой пакет
даёт пустой scratch, очистку пути и invalidation при обычном завершении тела.
Возврат 1 не означает, что путь существует или текстура загружена: загрузка
выполняется позднее соответствующим mesh helper с собственными gates.

## Короткие PlayMP3: значения и cursor

Таблица описывает результат статического исполнения readers для валидного
buffer заданного размера. Она не утверждает, что engine доставляет такие пакеты.

| Payload size | Byte-поля | COORD | STRING и cursor |
|---|---|---|---|
|0|Оба -1, cursor0|Ошибка, -0.125, cursor0|Пусто; bad1; play и loop трактуются как true|
|1|Первый доступен, второй -1, cursor1|Ошибка, -0.125, cursor1|Пусто; bad1; play=true|
|2|Оба доступны, cursor2|Ошибка, -0.125, cursor2|Пусто; bad1|
|3|Оба доступны, cursor2|Ошибка, -0.125, cursor остаётся2|Третий байт читается как STRING; cursor3; bad1 сохраняется|
|4|Оба доступны, cursor2|Успех, cursor4|Пусто без входного NUL; сам ReadString не ставит bad|

В случае size3 третий байт 0/0xff даёт пустую строку; другой байт становится
однобайтовым именем. Это важная связь между отказом ReadShort и последующим
STRING: «ошибка COORD» не означает пропуск оставшегося поля или отказ всего
сообщения. Для четырёх байтов полного header отсутствие строки не является
отдельной ошибкой decoder. Поведение внешнего музыкального backend по такому
имени этой таблицей не устанавливается.

## Сопоставление с найденным engine MessageEnd

После независимого чтения `decompiled/engine/captures/graphics-engine-wire/
010-pseudocode.c` установлен оригинальный MessageEnd 01da64aa. В ветке usermsg
с id>0x3a он ищет запись регистрации; при registered_size==-1 и staging payload
size>0xc0 вызывает nonreturn Host_Error01d7d873 **до** переноса в destination
(см. новый engine-message-followup-contract.md), а не обычный packetdrop. Для
принятого variable message пишет type byte, затем отдельный payload-length byte,
затем payload. Поэтому 192 относится к payload, а не к сумме с этими двумя
служебными байтами. Fixed-size сообщения имеют отдельную проверку точного размера.

Регистрация PlayMP3 и всех трёх CustomSlv/CustomFng/CustomGlv со значением -1
подтверждена напрямую в `decompiled/server/captures/chat-server-core/
002-pseudocode.c` (100e5fc0). Связь серверных engine slots с оригинальными
callbacks описана в `engine-wire-contract.md`; staging overflow и прочие ветви
отказа — в `engine-message-buffer-contract.md`.

Для обычного исходного engine route, успешно прошедшего эти проверки, при
отсутствии подмены callback/регистрации/данных после проверки получаем:

| Payload | Максимум полезных байтов имени при штатном NUL |
|---|---:|
|PlayMP3: два BYTE, двухбайтный COORD, STRING с NUL|187 =192-4-1|
|Один STRING CustomSlv/CustomFng/CustomGlv с NUL|191 =192-1|

Следовательно, **проблема несовпадения cap2047 и destination256 сама по себе
не достигается через такие штатно сформированные и доставленные пакеты**.
Даже если внутри уже ограниченного payload нет NUL, ReadString синтезирует его
после не более 188 байт для полного PlayMP3 header или 192 байт для custom path;
они всё ещё помещаются с NUL в 256. Это последнее утверждение относится только
к валидному buffer, callback size<=192 и указанному порядку полей. Оно не
доказывает, что engine вообще допускает некорректный payload к callback.

Замена имени через cl_downwiththesickness использует фиксированные 23 байта
`downwiththesickness.mp3`, также меньше 256. Напротив, прямой вызов handler с
большим size, иной engine или ещё не исследованный сетевой путь не ограничены
одним анализом MessageEnd. Условный raw pointer +c8, внутренний копирующий
цикл producer и полное владение handle остаются отдельными вопросами; локальная
граница strncpy не означает полную безопасность подсистемы.

### Разделение writer и decoder

Для writer, который гарантированно отправляет L байт строки и завершающий NUL,
арифметика payload такова:

- Custom texture: L+1 байт.
- PlayMP3: 2 BYTE + 2-байтный COORD + L+1, то есть L+5 байт, **если** оригинальный
  WRITE_COORD действительно сериализует signed16 в ожидаемом формате.

При максимальном успешно доставляемом payload M и отсутствии частичной доставки
получаем L<=M-1 или L<=M-5. Для проверенной ветки выше M=192. Значение 255,
знакомое по некоторым форматам однобайтовой длины, здесь не заменяет более
строгую проверку 192 в оригинальном MessageEnd.

Для гарантированного NUL после strncpy256 достаточно декодированной L<=255.
Вывод из общего M дополнительно требует корректного терминатора и поведения
при превышении M: writer может отказать, обрезать, вызвать fatal или сформировать
иначе. Если writer обрезает без NUL, ReadString всё равно создаёт терминатор в
scratch, но длина всех доступных байтов может быть на один больше ожидаемой по
формуле L+1. Поэтому утверждения о clip и null handling должны быть раздельными.

Текущий параллельный разбор engine закрыл обычный nonnull WRITE_STRING как
длину до NUL плюс сам NUL, и WRITE_COORD как trunc_toward_zero(8*x) с записью
младших 16 бит без signed16 clamp. Полные доказательства и ограничения области
float приведены в `engine-wire-contract.md`. Нельзя переносить только клиентский
диапазон -4096..4095.875 на аргумент writer: например, большее значение может
обернуться при сохранении младших битов.

Оставшиеся точные границы:

1. Последующие изменения BSS-байта 02079bcc, который engine копирует при
   WRITE_STRING(NULL); его первоначальный zero-fill доказан, неизменность нет.
2. Полный downstream transport и проверки malformed packet до callback,
   а также возможная подмена таблиц/регистраций после исходного bootstrap.
3. Необычные числовые состояния WRITE_COORD: NaN/Inf, выход за int64 и
   исключения x87; клиентский parser не решает поведение encoder.
4. Setjmp owner/recovery после engine nonlocal error transfer и дальнейшая судьба overflow
   staging; подробнее ограниченная модель в engine-message-buffer-contract.md.
5. Более узкие ограничения map strings/AllocString и внутренние destinations
   музыкального producer отдельно от сетевой границы.

Ни новый renderer, ни современный Xash автоматически не являются доказательством
этих гарантий для оригинального бинарника. Наблюдавшийся crash, уязвимость или
полная безопасность этим статическим проходом не заявляются.
