# Серверный `cof_blur`: фабрика, состояние, протокол и время

Статическая проверка 2026-11-20 по сохранённым C, чтению байтов PE и новым
REA/Ghidra captures `decompiled/server/captures/graphics-blur-server/`.
Оригинальная DLL не исполнялась.
Серверный `hl.dll` SHA256:
`751a68831e4fe3541bbbb24da3c785fb9f6cd3d7e6dcd92125fe1e18f0fce641`.
Хэш проверен до и после чтения. Адреса принадлежат оригинальной DLL.

## Привязка класса

Экспорт `cof_blur` — `100aa130` (физический диапазон всего 5 байт), фабрика —
`10090520`. Ghidra разворачивает фабрику и в псевдокоде экспорта: это не две
реализации эффекта. Фабрика выделяет `0xdc` байт private data, записывает
vtable в private+0 и указатель entvars в private+4. Артефакт `iRam00000004`
не следует трактовать как игровую глобальную переменную.

В `10090568` байты `c7 00 70 3a 1c 10` соответствуют записи таблицы
`101c3a70`. Сырые байты сохранены в `blur-server-pe-candidates.json`.
Новый capture подтверждает запись vtable (`000-procedure_assembly.json`),
все сырые слоты (`001-read_bytes.json`), Spawn (`002-pseudocode.c`) и Use
(`003-pseudocode.c`, полная assembly в `004-analyze_function.json`).
Названия слотов согласуются с ранее восстановленным ABI и телами методов.

| Слот | Адрес данных | Байты | Метод |
|---|---|---|---|
| Spawn +2c | `101c3a9c` | `f0 d5 09 10` | `1009d5f0` |
| KeyValue +34 | `101c3aa4` | `a0 db 00 10` | `1000dba0` |
| Use +e8 | `101c3b58` | `b0 5b 0a 10` | `100a5bb0` |

Все три тела уже имеются в `decompiled/server/partial-pass/functions/`.
`Spawn` ставит entvars+10c=0 (SOLID_NOT), +118=0x80 (EF_NODRAW),
+108=0 (MOVETYPE_NONE). Здесь именно присваивание effects, не OR.
Ни моделирование геометрии, ни планирование Think в этом теле не происходят.

`KeyValue` — общий обработчик `1000dba0`: распознаёт `movewith`, `skill`,
`style`; неизвестному ключу выставляет handled=0. Отдельных ключей
интенсивности или длительности blur здесь нет. Это не означает, что
обычные entvars key/value недоступны через общую обработку движка.

## Use и состояние игрока

`100a5bb0` требует ненулевого activator. Вызывает его виртуальную проверку
по слоту +d0 (в восстановленном ABI — IsPlayer); при нуле ничего не делает.
Через `100125e0(activator->pev)` получает player private data и выполняет:

```c
player->field_1ebc = (player->field_1ebc == 0);
```

Итог — строго 0 либо 1. UseType, value, caller, параметры самого cof_blur
в теле не читаются. Это переключатель **игрока-активатора**, не рассылка
всем игрокам. Сообщение непосредственно из Use не отправляется.
Таймера, fade, интенсивности и автономного завершения у этого Use нет.
Повторное использование переключает эффект обратно.

## Протокол Blur

Регистрация `100e5fc0`: global `10226574`, строка `101dad34`, размер 1.
Проверенные байты строки:
`42 6c 75 72 00 00 00 00 55 6e 72 65 61 64 53 4d` → `Blur`.
Предварительный кандидат global `10226600` к этой цепочке не относится:
новый `005-read_bytes.json` явно содержит в `101dae88` байты
`42 6f 6d 62 00 00 00 00 50 68 6f 6e` → **Bomb**, а не Blur.
Ссылки на этот посторонний global сохранены в `006-inspect_native_instruction.json`.

| Поле private player | Назначение в исследованной цепочке |
|---|---|
| +1ebc / DWORD[7af] | Текущее состояние blur |
| +1eb8 / DWORD[7ae] | Последнее отправленное состояние |
| +24cc | Флаг полной начальной синхронизации в 100f6ca0 |

`100ead70` сравнивает +1eb8 с +1ebc. При различии выполняет
`MESSAGE_BEGIN(MSG_ONE,10226574,NULL,player_edict)`, `WRITE_BYTE(+1ebc)`,
`MESSAGE_END`, затем копирует текущее значение в кеш +1eb8. Сеть передаёт
ровно один байт состояния, без длительности. Несколько переключений до
этой проверки могут схлопнуться в конечное состояние.

`100f4090` выставляет кеш +1eb8 в -1, заставляя следующую проверку отправить
текущее состояние. Прямого обнуления +1ebc в этом сохранённом теле нет.
`100f6ca0` при входном +24cc!=0 очищает этот флаг и в ветке полной
синхронизации посылает текущий +1ebc тем же MSG_ONE/BYTE. Эта отправка
не обновляет +1eb8 прямо в показанном месте, поэтому последующая отправка
по изменению не исключается. Не следует объявлять InitHUD сбросом blur.

## Морфин использует тот же флаг

`100e8d70` начинает dream только если BYTE player+2278==0 и blur +1ebc==0.
Он ставит +2278=1, deadline FLOAT +227c=time+30, blur +1ebc=1; задаёт
случайную дополнительную ветку (+2280, иногда +2270=time+random(5,20)),
обновляет sound timer +440, запоминает room_type в +2284 и ставит room_type=16.
Соседнее сообщение global102265e8 с байтами10,1 — отдельный эффект,
не пакет Blur. Его имя этим разбором не устанавливается.

`100ead70` при активном +2278 проверяет **time > deadline** (строго, не >=)
и вызывает `100f5c90`. До этого он поддерживает `player/morphine_dream.wav`
по таймеру +440 с интервалом11 секунд.
`100f5c90` работает только при активном +2278: очищает +2278,+2280,+227c,
+2274, останавливает звук, ставит blur +1ebc=0, восстанавливает room_type,
посылает отдельное сообщение102265e8 с0,0. Blur затем приходит обычной
синхронизацией состояния. Сброс таймера +2270 здесь не виден.

Вызов старта найден в `1007aab0`: проверяется связанное окно +2274 и
отсутствие активного dream. Полный контракт шприца здесь не переименовывается.
Эти 30 секунд принадлежат dream, **не общему cof_blur**. Оба механизма
используют один флаг без счётчика владельцев: map toggle во время dream
может выключить blur; завершение dream записывает0 независимо от предыдущих
map toggle. Активный map blur блокирует старт dream через проверку100e8d70.

## Сверка со справочником и пределы

`FUNCTION_CATALOG.txt` распознавал фабрику по шаблону, но не связывал методы
по числовой таблице. Новые результаты — в `blur-server-notes.json` и основном
справочнике; цепочка больших player functions дополнительно описана здесь.
`analysis/map-startup.json` подтверждает одну сущность
cof_blur в c_start, но не служит доказательством её параметров.

Клиентская сторона описана в `blur-triggers.md`: server byte, waterlevel и
Damage deadline — отдельные источники одного draw predicate. Полная
save/restore таблица +1ebc и все пути первоначального обнуления private data
ещё не установлены; отсутствие текстовой ссылки в partial-pass не доказывает
отсутствия записи в DLL. Runtime и визуальная проверка не проводились.

Источники: одноимённые C в `decompiled/server/partial-pass/functions/` для
`100aa130`, `10090520`, `1009d5f0`, `1000dba0`, `100a5bb0`, `100125e0`,
`100e5fc0`, `100ead70`, `100f4090`, `100f6ca0`, `100e8d70`, `100f5c90`,
`1007aab0`; raw evidence `analysis/graphics/blur-server-pe-candidates.json`.
