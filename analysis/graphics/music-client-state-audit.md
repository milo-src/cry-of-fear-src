# Музыкальное состояние: ограниченная проверка владельцев записей

Дата: 2026-11-20. Только статическое чтение оригинального client.dll,
SHA256 `e0d0ef0eac981bda321c834e7d73ad7a905cc66bcbed13706bc8e24eac284360`.
Игра и новые процессы REA не запускались. Общий каталог и старые документы
не изменены. Структурированный результат: [music-client-state-evidence.json](music-client-state-evidence.json).

Ненулевой writer музыкального byte `+c4` **не установлен**. Четыре внешних
кандидата из списка буквальных записей относятся к доказанным UI-путям.
В ограниченном звуковом диапазоне `1007f6e0..10080850` видны только два сброса
этого байта. Это не доказательство отсутствия иных записей во всей программе.

## Разделение владельцев одинакового смещения

| Инструкция | Настоящий вход | Подтверждённый receiver и действие |
|---|---|---|
|100023b1|10002340|UI-конструктор пишет byte[original ECX+c4]=1; инициализирует vtables и поля вплоть до+261|
|10003b26|10003b20|Setter пишет младший байт аргумента в ECX+c4, затем вызывает10003c90|
|100338ca|100338a0|Telephone handler пишет0 в `*(DAT101b2600+147c)+c4` перед разбором mode|
|100339e0|100338a0|Тот же telephone receiver получает1 только при mode3|
|1007f99c|1007f940|Audio activation сбрасывает context+c4 при ненулевом backend105440a8|
|100807c6|10080780|Stop сбрасывает ненулевой context+c4; receiver поступает из105440a4 через1007fc10|

UI-связь первых двух не получена из одних адресов или названий. В сохранённом
`vgui-menu-first/005-pseudocode.c` функция1003f850 создаёт CDifficulty,
использует checked/unchecked изображения и подпись Enable developer commentary.
ASM `difficulty-owner.asm` уточняет потерянный в C ECX: ESI=parent+cc,
ECX=ESI перед call10002340 по1003f8b4 и перед call10003b20(1) по1003f9cf.
Следовательно, эти две конкретные ветви обслуживают встроенный UI-контрол,
а не музыкальный объект. Полный перечень возможных callers этих методов
здесь не восстановлен; невозможность иных receivers не утверждается.

100338a0 имеет сохранённое C и карточку Telephone_MsgFunc в справочнике.
Помимо явной базы `[[101b2600]+147c]`, тело проверяет видимость через vtable,
воспроизводит telephone_receiver_up/down.wav, dial_tone.wav и копирует текст
в panel+cc. Положительная запись100339e0 не доказывает музыкальный режим:
её receiver не читается из105440a4. Формальной глобальной alias-проверки этих
двух указателей этот аудит не выполнял.

Для100807c6 AL равен0 не из предположения о bool: CheckParm возвращает EAX,
TEST EAX,EAX по100807af и JNE обходят ветку при ненулевом результате. По
нулевой ветке до записи AL не меняется. Запись+dd=1 не меняет EAX.

## Поля в ограниченном звуковом диапазоне

Проверены буквальные операнды `+0xc0/+0xc4/+0xc8/+0xd4/+0xd8` в
`1007f6e0 <= address < 10080850`:16 строк чтения/записи сохранены в JSON.

| Поле | Подтверждённые обращения |
|---|---|
|+c0, signed int|1007f992 пишет0;1007f907 читает, преобразует в float и делит на255 для override громкости|
|+c4, byte|1007f99c и100807c6 пишут0;1007f8fa,1008011f,100807be проверяют значение|
|+c8, pointer|1007f950 пишет0;10080128 сохраняет исходный track pointer при+c4!=0;10080143 читает для сравнения имён|
|+d4|1007f9b7 и100801c1 пишут0;1007fb8d пишет третий неотрицательный float-аргумент setter|
|+d8|1007f9c1 и100801cb пишут0;1007fb9f пишет четвёртый неотрицательный float-аргумент setter|

Ненулевой writer+c0 и reader+d4/+d8 этим диапазоном не установлены. Сохранение
+c8 не является копированием или владением строкой; данная ветка не вызывает
новый allocation. Update не читает+c8 и не исполняет сохранённый запрос.
Поля+d4/+d8 пока имеют доказанную связь setter/reset, без выдуманного значения
«fade-in» либо «crossfade». Подробные существующие ветви play/stop изложены в
[music-client-contract.md](music-client-contract.md).

## Границы доказательства и полезные следующие вопросы

- Список465 кандидатов — набор буквальных смещений многих разных классов.
  Этот проход классифицировал шесть byte+c4 кандидатов и узкий audio span;
  он не присваивает все465 записей аудиообъекту.
- Поиск не исключает adjusted-base/alias записи, wider stores, bulk copies,
  indexed addresses, непрямые или внешние вызовы и пропущенные дизассемблером
  code paths. Поэтому нельзя назвать+c4 недостижимым, мёртвым или всегда0.
- При необходимости продолжения точная граница — возможный escape receiver
  из1007f6e0/1007f940 и аргументы/receiver вызовов из1007f740/1007fd50;
  нужен анализ потока адресов, а не ещё один поиск текста+c4. Кто владеет
  строкой+c8 и кто вызывает альтернативный10080300, остаётся отдельным вопросом.
- UI helper10003c90 и дополнительные UI callers не нужны для вывода о
  показанном difficulty receiver; дальше этот несвязанный UI не исследовался.

## Проверка сохранённых доказательств

Восемь ограниченных ASM-фрагментов лежат в `music-client-state-assembly/`.
Они извлечены из уже сохранённого `analysis/local/music-state-client-text.asm`.
Каждый байт каждого диапазона сопоставлен с исходным PE; metadata содержит
SHA256 DLL, исходного listing, списка кандидатов, каждого ASM и бинарного
диапазона, адрес начала и исключительную верхнюю границу. Исходный DLL
прочитан только для проверки байтов. Полные C-файлы подтверждают смысл ветвей;
ASM закрывает конкретные receivers и значения регистров.
