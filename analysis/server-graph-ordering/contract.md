# Подготовка связей и перестановка узлов навигационного графа

Статический разбор трёх ранее не проверенных функций оригинального серверного `hl.dll`. SHA-256: `751a68831e4fe3541bbbb24da3c785fb9f6cd3d7e6dcd92125fe1e18f0fce641`. Исходные C не изменялись, DLL не запускалась. `capture.py` сохраняет ограниченные дизассемблированные диапазоны и сверяет каждую машинную строку с PE; `evidence.json` фиксирует хеши C, ASM, сырые константы и таблицу ENTVARS. Уверенность high относится к локальным ветвям и ABI, а не к корректности графа на всех картах.

Первичные функции: `100ce420`, `100cebc0`, `100cf310`. Поддержка: вызывающий builder `100ca860`, адаптер TraceLine `1011a800`, инициализация engine API `100b4aa0`. Полный [контракт builder и bodyqueue](../server-graph-builder/contract.md) принадлежит отдельному пакету; здесь его тело используется для установления порядка вызовов и предусловий. См. также [жизненный цикл графа](../server-graph-lifecycle/contract.md), [служебные операции](../server-graph-helpers/contract.md) и [поиск пути](../server-monster-pathfinding/contract.md).

## Владение данными и композиция

Во всех трёх методах ECX — граф, обычно глобальный `102238b0`. Его `+0c` — массив узлов, `+10` — окончательный массив связей, `+18/+1c` — signed DWORD количества. Узел имеет размер `0x58`: position `+00`, visibility position `+0c`, три байта пространственных корзин `+18..1a`, category `+1c`, count/firstLink `+20/+24`, восемь смещений маршрутов `+28..44`, временная стоимость `+48`, временный индекс/предшественник `+4c`, два SHORT hint `+50/+52`, yaw `+54`. Назначение padding `+1b` как игрового поля не установлено. Связь `0x18`: source/destination `+0/+4`, entvars* препятствия `+8`, первые четыре байта имени brush model `+0c`, hull mask `+10`, float cost `+14`.

`100ce420` и `100cebc0` получают отдельный рабочий link buffer через стек, не используют `graph+10` как его замену и не владеют его временем жизни. `100cf310` работает уже с окончательными `graph+0c/+10`. Эти три функции не выделяют и не освобождают массивы. У `100ce420` есть дополнительная зависимость от глобального указателя узлов `102238bc`: записи count направлены туда, даже если ECX обозначает иной граф.

В сохранённом builder порядок следующий: сброс count/firstLink/route offsets у глобальных узлов; подготовка категорий и координат; `100ce420`; отдельная проверка проходимости для hulls; `100cebc0`; вычитание числа отброшенных связей; выделение окончательного массива и компактное копирование активных диапазонов с обновлением firstLink; `100cf310`; построение хеша пар; построение пространственных корзин. Затем только у category&1 из position.z вычитается 8, visibility position.z сохраняется, и уже после этого рассчитываются сжатые маршруты. Следовательно, локальное отсутствие reset count и проверок NULL log у `100ce420` не означает, что нормальный builder подаёт именно такие входы: он обнуляет count и прекращает работу при неудачном открытии журнала. Однако сами локальные функции эти предусловия не обеспечивают.

## 0x100ce420 — Graph_ConnectVisibleNodePairs [high]

Создаёт направленные связи между узлами одной категории по трассировке в обе стороны; сохраняет препятствие, если обе трассы упёрлись в одну и ту же не-worldspawn сущность. Возвращает общее количество связей, а при локально обработанной ошибке — 0 с индексом проблемного узла через выходной указатель.

ABI: ECX=graph; три стековых аргумента `(linkBuffer, FILE* log, int* outBadNode)`; `RET 0x0c`, результат EAX. `*outBadNode=0` выполняется до любых проверок, NULL выходной указатель не допускается. Signed `nodeCount<=0` печатает AlertMessage с severity 2 и возвращает 0. NULL log вызывает предупреждение, но не ранний возврат. Это не безопасный режим отключённого журнала: итоговые два fprintf, а также fprintf ветки 128 связей вызываются без проверки log. Соседний [CRT-контракт](../server-graph-builder/contract.md) подтверждает проверку NULL stream в backend `1015cc01`, запись errno-like 22, вызов invalid-parameter helper и -1 при его возврате. Полное поведение invalid-parameter handler и реальный эффект этого входа не проверялись.

Для каждого source в исходном порядке локальный count начинается с нуля. Начиная с `buffer+total*0x18`, функция заранее инициализирует 128 записей: source=текущий индекс, destination=0, entvars*=NULL. Поля modelTag, hull mask и cost этой инициализацией не затронуты. Узлу `this.nodes[source]` записывается firstLink=total. Затем все destination перебираются по возрастанию, кроме source; пара допускается к трассам только при `((src.category XOR dst.category)&7)==0`. Это сравнение трёх младших битов, а не проверка общего пересечения категорий.

Первая трасса: `TraceLine(src.position, dst.position, 1, [10231f60], &trace)`. Адаптер `1011a800` заменяет mode на результат equality-to-1 и хвостом вызывает engine API `10222fc4`, слот 31 от базы `10222f48`; здесь переданная 1 сохраняется. Игнорируемая сущность поступает из глобального указателя. Его writer теперь раскрыт отдельно: `101207e0` создаёт кольцо из четырёх `bodyque` edicts с next в entvars.owner+19c и сохраняет первый в `10231f60`; `10120500` копирует тело в текущий и сдвигает cursor. Это текущий элемент bodyqueue, а не специально созданный test hull или гарантированно world/NULL. Подробности и отдельные доказательства — [builder/bodyqueue](../server-graph-builder/contract.md). `trace+4` (startsolid) ненулевой — отказ; allsolid отдельно не проверяется. Ordered `trace.fraction==1.0f` — принять сразу. UCOMISS/LAHF/TEST 44/JNP в `100ce56a..575` не принимает NaN как единицу.

Если первая fraction не равна единице, сохраняется hit edict (`trace+30`) и делается обратная трасса с теми же mode/ignored entity. Для допуска достаточно совпадения двух hit edict, после чего classname сравнивается с точной строкой `worldspawn` с учётом регистра. Worldspawn отвергается. Иная сущность принимается: в link+8 сохраняется edict+80 (entvars), в link+0c копируется именно DWORD из начала model string, а не string_t/указатель. У entvars.flags `+1a8` добавляется `0x10000`, если этот бит отсутствовал. Это flags, не spawnflags `+1a4`; имена подтверждены сырой ENTVARS. Обратные fraction/startsolid/allsolid не используются как самостоятельные ограничения. Совпавшие NULL hit edict не имеют защиты: после формирования NULL entvars код читает classname через NULL. Не заявляется, что штатный engine trace способен выдать такой набор.

Журнал при принятии связи печатает destination. При сохранённом entvars и ненулевом `EntOffsetOfPEntity(entvars.edict+20c)` добавляет classname, targetname и model через poolbase `gpGlobals+98`; соответствующие смещения entvars `0/1d0/b8`. Затем локальные count и total увеличиваются, destination записывается в текущую связь, указатель продвигается на `0x18`. При `count==128` уже записанная 128-я связь приводит к Alert 2, fprintf, `outBadNode=source`, EAX=0; обычная запись node.count ниже ещё не выполнена, поэтому после нормальных предыдущих итераций там остаётся 127. Далее проверяется signed `total > (nodeCount<<7)` с машинным 32-битным переполнением; при истинности тоже outBadNode=source и 0. Проверки стоят после записи, не перед ней; выделенного размера buffer функция не получает.

На обычном пути обновляется максимум локальных count и выполняется запись `globalNodes[source].count=count` через абсолютный `102238bc` (`100ce744..752`). Если нет ни одной принятой связи, count этого source здесь вообще не сбрасывается; firstLink всё равно обновлён. Ветка `count==0` с текстом «NO INITIAL LINKS» находится после успешного increment и после проверки `count==128`; при обычном конечном переборе от нуля не достигается. При отказе отсутствует rollback уже записанных связей, firstLink/count и flags сущностей. Успех с нулём связей и ошибка имеют один EAX=0; outBadNode=0 тоже не различает их надёжно. Builder трактует 0 как failure.

Доказательства: `100ce420.asm` целиком, особенно `100ce4e2..4f1` (частичная инициализация), `100ce55b..65a` (трассы), `100ce6fc..752` (порядок mutation/guards), `100ce7aa..820` (return paths). Полная логика engine TraceLine, CRT и пригодность принятых препятствий для пути находятся вне этой функции; отдельный walk/hull pass следует позже.

## 0x100cebc0 — Graph_RejectLongerCollinearXYLinks [high]

Удаляет более длинную исходящую связь, когда другая связь того же узла имеет почти одинаковое нормированное направление в плоскости XY; активный диапазон сокращается заменой удалённой записи последней. Возвращает число удалённых связей и записывает двумерную длину в cost рассматриваемых записей.

ABI: ECX=graph; `(linkBuffer, FILE* log)` в стеке; `RET 8`, EAX=число удалений, включая 0 при signed nodeCount<=0. Для каждого source берутся this.nodes и его count/firstLink. Вычисляется `dx=dst.x-src.x`, `dy=dst.y-src.y`; Z, visibility position, препятствие, hull mask, category и наличие ребра между двумя destination не участвуют. Сумма `dy*dy+dx*dx` вычисляется SSE single, затем расширяется до double для SQRTSD и снова округляется до float. Только ordered zero длины даёт direction=(0,0). Иначе применяется single `1.0f/length`, затем single умножение компонент; NaN идёт по ветке деления. Отрицательный аргумент корня направляется в `1016be90` (__libm_sse2_sqrt_precise по сохранённой идентификации), unordered — в SQRTSD; внутренний CRT math не разобран.

Перед сравнением с соседями текущей записи пишется cost=эта XY length. Для каждого другого активного ребра заново вычисляется его XY direction и length. Dot — single сумма произведений, расширенная в double. Удаление требует ordered `dot >= double(0.998)` и ordered `currentLength > otherLength`. Порог в PE `101d7638`: восемь байт зафиксированы evidence. COMISD/JB (`100cee04..0c`) и COMISS/JBE (`100cee18..1b`) отвергают unordered; NaN не трактуется как совпавшее направление или меньшая длина. Равные длины не удаляются. Нулевой вектор обычным сравнением не проходит порог.

Удаление копирует все `0x18` байт последней активной связи этого source поверх текущей через MOVUPS+MOVQ. Count узла уменьшается на 1; текущий индекс сначала декрементируется, затем внешний increment возвращает его на ту же позицию. Поэтому подставленная последняя запись обрабатывается заново; внутренний цикл прекращает дальнейшие сравнения удалённой записи. Число удалений увеличивается, но graph.linkCount и firstLink не пересчитываются. Физические хвосты диапазонов остаются в рабочем buffer, глобальная упаковка выполняется builder позже. Перестановка нарушает прежний порядок рёбер и может влиять на последующее назначение node IDs.

Все fprintf защищены ненулевым log. В C у «Node %3d» потерян аргумент; native `100cec2b` выполняет PUSH EBX с индексом source, затем PUSH format и FILE*, поэтому дефект varargs здесь не утверждается. Отсутствуют проверки NULL graph/buffer, индексов destination, отрицательных firstLink, соответствия count реальному размеру. Данные изменяются на месте, отдельного failure status и rollback нет. Алгоритм не доказывает сохранение достижимости для каждого hull/препятствия: он сравнивает только XY-направление и длину.

Доказательства: `100cebc0.asm` целиком, арифметика `100cec66..ced15`, повторная нормализация `100ced6b..cedfd`, predicates `100cee04..1b`, замена/повтор `100cee6c..ceec6`. Сохранённый caller показывает вычитание EAX из общего числа и последующее компактное копирование активных диапазонов.

## 0x100cf310 — Graph_RenumberNodesByDestinationEncounter [high]

Назначает узлам новые индексы по порядку первого появления в исходящих связях, переписывает source/destination всех связей и переставляет полные записи узлов на новые места. Это последовательный обход исходных массивов, не обход графа в ширину и не сортировка по расстоянию.

ABI: ECX=graph, явных стековых аргументов нет, обычный RET. Фиксированного success результата функция не формирует; EAX остаётся побочным значением последней ветки. Сначала без проверки count или nodes выполняется `nodes[0].field4c=0`. Узлам 1..N-1 записывается -1. NextRank начинается с 1. Затем source перебираются в исходном физическом порядке 0..N-1; их исходящие links идут в порядке firstLink..firstLink+count-1. Если destination.field4c==-1, ему присваивается NextRank++. Присвоение не меняет порядок обхода source. После этого всем ещё не отмеченным узлам по исходному индексу назначаются оставшиеся номера. При валидных массивах это создаёт old→new permutation с неизменным номером 0 для старого узла 0.

Перед физической перестановкой выполняется отдельный проход по всем graph.linkCount связям: и source+0, и destination+4 заменяются на соответствующие nodes[oldIndex].field4c. Затем для каждой физической позиции i, пока nodes[i].field4c!=i, выполняется swap nodes[i] с nodes[nodes[i].field4c]. Свойство permutation обеспечивает завершение только при корректных входных данных. Link buffer при этом не сортируется и не переставляется. Count/firstLink перемещаются вместе с узлом, поэтому его прежний диапазон рёбер остаётся доступным, а source этих рёбер уже переименован.

Обмен охватывает position, visibility position, category, count/firstLink, все route offsets, cost, поле4c, SHORT hints и yaw. Имеется точное исключение для байта выравнивания +1b: при сохранении целевой записи во временный stack node код пишет WORD+18 и BYTE+1a, но не пишет byte `[ebp-45]`, соответствующий +1b. Затем stack temporary целиком возвращается в исходный узел через MOVUPS/MOVQ. Поэтому node+1b на этой стороне обмена берётся из ранее неинициализированного в данном frame stack byte; противоположная сторона копируется полностью из исходной записи. Это подтверждено `100cf43c..44d`, `100cf504..508`; остальные записи temporary данный байт не покрывают. Неизвестно, читается ли padding игровым кодом; нельзя превращать этот факт в утверждение о нарушении маршрутизации. Копирование сериализуемой записи, однако, не гарантирует побайтового сохранения padding.

После успешного цикла node[i].field4c==i. Старое→новое соответствие отдельно не сохраняется. Route offsets копируются как есть и не пересчитываются; уже существующие route streams, хеш пар и пространственные индексы функция не перестраивает и не инвалидирует. В штатном builder они строятся после неё, поэтому её нельзя без дополнительных условий применять к полностью готовому графу. Отсутствуют проверки NULL, nodeCount>=1, диапазонов source/destination/count/firstLink, допустимости permutation и ограничение числа swap. Даже count<=0 не предотвращает первоначальную запись nodes[0]+4c. Ошибка/rollback не предусмотрены; повреждённые индексы могут привести к выходу за массив или незавершающемуся циклу, но runtime такое не проверялся.

Доказательства: `100cf310.asm` целиком; первая запись `100cf325`, присвоение по destinations `100cf360..3ae`, остаточные номера `100cf3c0..3d8`, remap `100cf3e3..410`, swaps `100cf430..535`. Caller `100ca860.asm` подтверждает ECX глобального графа при вызове и размещение между компактизацией и построением хеша.

## Границы доказательства

Все три локальных тела прочитаны вместе с машинными ветвями; новых запросов Ghidra не понадобилось. Не утверждаются runtime parity, полнота восстановленного графового класса или безопасность повреждённых графов. Открыты полное поведение engine TraceLine, CRT fprintf/math/allocator и все внешние consumers padding byte+1b. Producer ignored edict `10231f60` и его изменение через bodyqueue закрыты соседним пакетом; полный lifecycle всех bodyque entities остаётся отдельным вопросом. Подготовка hull masks, освобождение временного buffer и глобальные failure states принадлежат builder, а не этим трём карточкам.
