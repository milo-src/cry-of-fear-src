# Карта реверса игрока: движение, стамина, HP и лестницы

Основной рабочий справочник: `decompiled/FUNCTION_CATALOG.txt`.
Этот файл — короткий маршрут к его карточкам и более подробным доказательствам.
Статический разбор от 2026-11-19 теперь использован в нативной реализации.
Текущий перенос и команды сборки/проверки: [implementation.md](implementation.md).
Проверки собственной игры не означают доказанного совпадения с оригинальным DLL.

## Быстрый вход

```powershell
python tools/catalog_decompiled.py --mechanic movement
python tools/catalog_decompiled.py --mechanic vitals
python tools/catalog_decompiled.py --mechanic ladders
python tools/catalog_decompiled.py --show server:0x100f4d70
python tools/catalog_decompiled.py --show server:0x10006520
python tools/catalog_decompiled.py --show server:0x1004ed40
```

Все адреса — preferred VA оригинальных PE32, модуль обязателен.
Одинаковые числа в разных DLL не означают одну функцию.

## Что нельзя упрощать при реконструкции

1. Спринт допускается с stamina≥1, хотя старт снимает5; серверный jump
   снимает15 без собственного порога15, а dodge требует≥15. Это разные guards.
2. Расход, проверка истощения и clamp идут в определённом порядке.
   Отрицательное значение и ровно0 дают разные промежуточные состояния.
3. Stamina обновляется дискретными ticks, не через единую формулу `rate*dt`.
   Пропущенные ticks не компенсируются циклом.
4. Heal queue использует **целочисленный** last-time. Нельзя записывать
   «5HP каждые0.1s» как установленный факт: в части секунды шаг повторяется
   при каждом вызове. Это подтверждено инструкциями conversion.
5. Физика прыжка и серверные расходы/анимация находятся в разных функциях.
   Клиентский HUD не определяет серверное здоровье или stamina.
6. `cof_ladder_manager` не является просто вертикальной скоростью `func_ladder`.
   Он переключает камеру и анимации, читает команды направления, затем
   переносит игрока к заданной конечной сущности.
7. Нельзя вставить структуры обычного HL SDK без сверки ABI: usercmd CoF
   имеет размер0x38, найдены дополнительные clientdata/weapon-data поля.

## Доказательства и уверенность

Существующий серверный корпус сохранён без редактирования.
Новые выборки клиента — `decompiled/client/captures/movement-client-*`,
в каждой `capture.json` с SHA-256 исходного DLL, SHA-256 файлов и REA Evidence ID.
В pass1 девять callbacks не распознаны как процедуры Ghidra; это отражено
в omitted_queries, их ветки изучены ограниченным disassembly в `client-static`.
Отсутствие процедуры в инвентаре не означает отсутствия кода.

Дополнительные статические чтения: `physics-evidence/capture.json`,
`health-evidence/capture.json`, `ladders-static.json`, `client-static/capture.json`.
Три пары Jump/CheckParameters/WalkMove дали совпадение нормализованного
псевдокода server/client (`prediction-comparison.json`). Это не runtime parity
и не доказательство идентичности всех глобальных данных.

Реализация сохраняет согласованный ABI нашего SDK/движка и переносит семантику
оригинала, не копируя его смещения объектов. Следующие задачи: подключение
состояний оружия и морфина к реконструированному инвентарю, сравнение поведения
с оригиналом, визуальная оценка камеры и проверка сохранения посреди подъёма.
Нерешённые вопросы перечислены в отчётах и карточках справочника.
