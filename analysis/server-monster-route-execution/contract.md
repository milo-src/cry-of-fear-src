Оригинальный server hl.dll SHA256 `751a68831e4fe3541bbbb24da3c785fb9f6cd3d7e6dcd92125fe1e18f0fce641`. Только статический анализ, без запуска DLL/игры и изменений ресурсов.

M=private object в ECX, V=[M+4], G=[10223188]. Offsets, masks и addresses hex; физические константы и counts decimal. f32 означает native scalar float32 rounding. Native descriptors закрепляют Mf0=m_flGroundSpeed, M210=m_flMoveWaitFinished, M218=m_IdealActivity, M22c=m_iTaskStatus, M2d0=m_movementActivity, M304=m_afCapability. Inline route:8 records по16 bytes, positionM238+16*i, flagsM244+16*i, cursorM2bc, goalM2b8. Поля M368..37c названы по наблюдаемому употреблению, без придуманного native save-field имени.

## Связи и доказанный dispatch

Concrete CGenericMonster vtable101ce36c, подтверждённая RTTI и factory100b05e0, связывает +164→100c2390, +16c→100155d0, +168→10013510 (EAX1), +15c→100c0750 и +160→100c0e70. [Move100c0750](../server-monster-movement/contract.md) передаёт исходный planar distance в virtual164 и только при ненулевом ответе вызывает100bc290. В нескольких failure/stop ветвях вызывает virtual16c. Другие overrides не исключаются.

Для100ab8b0 установлен полный локальный flying/ground dispatch и совместимый трёхаргументный ABI, но конкретная vtable/class binding здесь не доказана. Сохранённый exact-LE32 scan по raw .rdata/.data не находит самого preferred-base адреса100ab8b0. Это ограниченный отрицательный результат, не доказательство dead code, отсутствия динамических указателей или всех callers. Support100ab880 прямо вызывает100c0750 и при movetype5 перед этим копирует M374→Mf0; аналогичность расширенных offsets не является самостоятельным доказательством конкретного CFlyingMonster symbol/vtable. Shared vector10222f34..3c находится в virtual zero-fill части .data; его runtime writers/value здесь неизвестны.

## 0x100bc290 — Monster_AdvanceRouteCursorOrCompleteMovement

ABI: ECX=M, один stack float distance, RET4; общего нормализованного EAX/bool результата нет. На graph-ветке `[EBP+8]` переиспользуется как DWORD out-link-index, уничтожая первоначальные float bits аргумента. Это stack alias, не численное преобразование distance в link index. Нет проверки M/V или общего диапазона route cursor.

Первым сравнить signed bits M2bc с точным7. При равенстве вызвать RefreshRoute100bddb0(M); ненулевой EAX завершает функцию сразу. Ноль печатает AlertMessage(2,"Can't Refresh Route!!\n") и также return. В этой ветке нет чтения terminal flag/distance, собственного cursor increment, постановки failure condition или последующего продолжения нового маршрута в том же вызове. RefreshRoute может сам изменить route/cursor/goal согласно своему [контракту](../server-monster-navigation/contract.md).

Для cursor!=7 прочитать DWORD flags текущего waypoint. TEST AL,AL/JS проверяет только low-byte bit0x80, не знак всего DWORD. Если bit0x80 установлен, вычислить double(Mf0)*native double0.2 и сравнить с double(distance); только ordered произведение>distance вызывает100c1150(M), иначе return. Равенство и NaN не завершают movement; отрицательные значения не отфильтрованы. На этой ветке cursor не увеличивается. Support100c1150 по task status0/1 ставит3, по2 при отсутствии condition40000000 ставит4, по3 печатает предупреждение; на обычном возврате всегда очищает M2b8. Caller не очищает весь route и не вызывает Stop сам.

Если bit0x80 сброшен, проверить exact `(flags & 0xfffffe7f)==0x10`. Тогда взять C=[M+c], вызвать C.virtualdc() без NULL/serial guard, перечитать M2bc ПОСЛЕ callback и записать возвращённый EAX в M+c. В остальных случаях использовать начальный cursor. Затем проверить bit0x20 у текущей и следующей route-записи; эти flags читаются заново, а не берутся из исходного flags snapshot. При отсутствии хотя бы одного bit перейти к общему increment. Нет защиты для отрицательного или слишком большого cursor, а специальное число7 было обработано только до callback.

Если оба waypoint имеют bit0x20, выполнить graph102238b0→100cd530(&currentRoute.position,M), сохранить полный EAX как source node. Заново прочитать M2bc, затем graph→100cd530(&route[M2bc+1].position,M) как destination node. Между двумя nearest-query callbacks current index может измениться, поэтому нельзя заменить это заранее сохранённой парой соседних positions. Возвраты-1 или другие значения здесь не фильтруются перед следующей операцией. Graph pointers/индексы и доступность сети — граница нижних contracts, не локальная гарантия.

Graph→100cdcb0(source,destination,&stackDistanceSlot) пишет signed link index в бывший аргумент distance (RET12); native helper делает signed extension WORD hash entry и записывает DWORD, его EAX caller не использует. Только output>=0 позволяет загрузить link entvars pointer из `[102238c0]+24*index+8`. Если он ненулевой, вызвать graph→100cd990(source,linkEntvars,current M304,0). При ненулевом результате заново прочитать link index из stack slot и link-array pointer102238c0, затем заново прочитать entvars pointer той же записи. Лишь если новый pointer тоже ненулевой, вызвать100c11d0(M,linkEntvars) и сохранить ST0→float32 в M210. Поэтому pointer до link-policy callback не считается неизменным; верхней проверки link index нет.

Support100c11d0 разрешает entity по переданному entvars, вызывает его virtuale8 с четырьмя arguments `(M,M,1,float0)`, может обходить связанные entities и вызывает их Use, затем возвращает ST0 deadline относительно свежего времени. Это потенциально реентерабельная граница; полный body helper не получает новую карточку здесь. После всех graph исходов — negative link, NULL entity, policy false, успешный Use — выполняется INC DWORD[current M2bc] и return. Увеличивается свежая память, а не прежний saved cursor; при32-bit overflow native wrap не предотвращается. После callback нет повторной проверки terminal/goal/task status.

## 0x100155d0 — Monster_SetIdealActivityFromStoppedActivity

ABI: ECX=M, без stack arguments, plain RET. Сохранить исходный M в ESI, прочитать vptr и вызвать virtual168() с ECX=M. После возврата записать полный EAX в исходный M218=m_IdealActivity. Ни эта MOV, ни POP ESI не изменяют EAX, поэтому нормальный результат callback сохраняется в EAX, вопреки Ghidra void. Сам helper не нормализует значение до bool и не выбирает константу самостоятельно.

Concrete Generic virtual168=10013510 даёт EAX1, но для dynamic object возможен другой callback/result. Вызывающий dispatch virtual16c из Move соответствует stop/idle selection только в смысле назначения ideal activity. Здесь нет изменения velocity/origin/route/goal/таймера, SetActivity/animation reset или проверки camera freeze. Callback может менять или освобождать M; запись в сохранённый указатель всё равно выполняется, guard/reentrancy защиты нет.

## 0x100c2390 — Monster_ShouldAdvanceWaypointAtEightUnits

ABI: один stack float distance, RET4, ECX не читается. MOVSS constant8.0f@101a1ed8, XOR EAX,EAX, COMISS(8.0f,distance), SETAE AL возвращают полный EAX0/1:1 только для ordered distance≤8, включая отрицательные значения и -infinity. NaN возвращает0; +infinity0; equality8 даёт1. Нет absolute value, lower clamp, epsilon, отсылки к groundspeed или проверки route flags.

В concrete CGenericMonster это virtual164. Parent100c0750 передаёт сюда D=planar route distance, не clipped lookahead, не probe blocked distance. При1 parent вызывает100bc290(D), где terminal completion имеет другой threshold double(Mf0)*0.2; эти два tests не следует объединять. Функция не пишет memory и не вызывает helpers. При unmasked FP exceptions COMISS может иметь аппаратную exception-семантику; данный локальный контракт описывает обычный masked arithmetic path, MXCSR здесь не меняется.

## 0x100ab8b0 — Monster_ExecuteFlightMomentumOrGroundSteps

ABI: ECX=M, stack `(targetPrivate,directionPointer,float interval)`, все exits RET12; EAX не является устойчивым success/count. Сохранить входной V=[M+4]. Если cached V.movetype108!=5, вызвать100c0e70(M,target,direction,interval) с исходными bits/указателями и return. Полный наземный executor уже разобран [здесь](../server-monster-movement/contract.md); его собственные class/skin guards и игнорирование первых двух arguments не переносятся на flying path. Перед данным dispatch нет общего NULL/freeze/health/finite guard.

Для movetype5 сохранить G. Вычислить float32(now−M378); только ordered result>1.0f И M218!=M2d0 переводят M218=M2d0, затем M374=200.0f и Mf0=200.0f, после чего перечитывается G. Равенство1 и NaN не входят в reset. При остальных случаях эти поля не меняются этим этапом. M378 играет роль сохранённого времени остановки/снижения скорости, но точные producer/save names и concrete class не выводятся из сходства с SDK.

Вычислить смешанный vector A покомпонентно: `A=f32(f32(M[368..370]*M37c)+*directionPointer)`. Это три отдельных multiply/add, без clamp/magnitude limit и без guard directionPointer. Первая длина вычисляется именно в порядке `f32(f32(Ay*Ay+Ax*Ax)+Az*Az)`, затем расширение в double и SQRTSD, затем float32 length. Ordered negative square-sum идёт через1016be90; NaN идёт через SQRTSD. Только ordered length==0 даёт normalized=(0,0,1); иначе reciprocal=f32(1/length) и три float32 произведения. Ненулевой/NaN vector не заменяется безопасной константой.

Вычислить stepDistance=f32(current Mf0*interval), затем local endpoint E=cached V.origin+normalized*stepDistance с float32 операциями. Endpoint полностью инициализирован в native stack; Ghidra fStack/local aliases не означают uninitialized XYZ. Эти origin и stepDistance берутся ДО последующего speed-approach и local probe; callback не приводит к автоматическому пересчёту E. Отдельно загрузить cached G.frametime+4 и сравнить current M218 с M2d0.

Если ideal activity отличается от movement activity, вычислить delta=f32(G.frametime*75.0f), вызвать cdecl101174a0(target100.0f,current M374,delta), принять ST0 и округлить его в float32, затем записать M374. Только ordered result<100.0f ставит M378=fresh G.time; при равенстве или NaN timestamp не меняется. Если activities равны, вызвать тот же helper с target20.0f и delta=f32(G.frametime*300.0f), сохранить ST0→M374 без timestamp update. Это буквальные100/20 и75/300, а не интуитивно ожидаемые ускорение/торможение. В обеих ветках Mf0 НЕ обновляется этим helper stage; уже сформированный endpoint не использует новый M374.

Support101174a0 принимает три stack floats и возвращает ST0: d=f32(target−value); при ordered d>delta возвращает f32(value+delta); иначе при ordered -delta>d возвращает f32(value−delta); иначе target. Sign flip делается XOR sign mask, не fabs. Negative/NaN delta не запрещены; при unordered comparisons оба перехода могут не сработать и вернуть target. Caller отдельно округляет ST0 в float32. Безусловный clamp к положительной скорости или max step здесь не введён.

Затем свежий M.virtual158 получает `(&current V.origin,&local E,targetPrivate,NULL)`. Это POINTER Vector, не BY VALUE. Ненулевой EAX, в том числе код1, отрицательный и2, считается успехом; это отличается от100c0750, которому нужен ровно2. Для concrete100bd590 code1 обозначает height discrepancy после успешного local walk. E и origin могут быть изменены callback; subsequent native reads берут уже содержимое local E после его возврата. На flying path не выполняются detour, повторный probe или деление на16-unit шаги.

При nonzero probe заново загрузить V и записать в M368/M36c/M370 raw vector `local E−current V.origin`. Затем вычислить его float32 sum-of-squares в порядке x²+y²+z², double SQRTSD (ordered negative→helper), float32 length; только ordered0 заменяет result на(0,0,1), иначе reciprocal normalization. Повторно записать normalized vector в те же поля, так что raw delta действительно записывается до окончательного normalized результата. Нет интерпретации Ghidra неинициализированных locals: native использует E из сохранённого endpoint stack.

После нормализации повторно прочитать current Mf0 и исходный interval, вычислить float32 distance и вызвать10119420(cached-after-probe V.edict,&E,distance,1) ровно ОДИН раз. Это может быть другой distance, чем использованный для E, если callback изменил Mf0.10119420 копирует E в отдельный scratch и передаёт engine MoveToOrigin; engine return caller не проверяет. Нет positive/nonzero/finite distance guard, повторного local probe, route-goal check, изменения M374 после движения или feedback по фактическому origin. Нормализуется желаемое смещение до engine movement, не измеренное перемещение после него.

При probe EAX==0 вызвать свежий virtual168(), записать результат в M218, затем M378=fresh G.time, затем скопировать shared vector10222f34..3c в M368..370. Запись не объявляется гарантированным обнулением: raw PE показывает zero-fill storage, но runtime значение не доказано. Уже обновлённый M374 не откатывается; Mf0 тоже не восстанавливается. Generic stop helper100155d0 здесь не вызывается напрямую, а выполняется эквивалентная activity-запись с дополнительными timestamp/vector effects. Никаких route/goal/condition failure flags эта ветка не устанавливает сама.

## Остаточные границы и воспроизведение

Полные четыре primary закрыты по native local branches/ABI. Связанные ранее разобранные [navigation](../server-monster-navigation/contract.md), [graph helpers](../server-graph-helpers/contract.md), [pathfinding](../server-monster-pathfinding/contract.md), [route insertion и door wait100c11d0](../server-monster-controls/contract.md) и [movement](../server-monster-movement/contract.md) остаются отдельными карточками. Полный owner/producers M368..37c остаётся границей следующего связного прохода; bounded usage не считается самостоятельным новым REVIEW. Уже разобранные100bf8c0 и100c11d0 не входят в pending этого пакета.

Не доказаны конкретный native class/vtable100ab8b0, все indirect overrides, внешние engine MoveToOrigin/trace/time/lifetime guarantees и runtime shared-vector writers. Отрицательный raw-pointer scan не заменяет полноценный граф ссылок. Воспроизведение: capture.py→write_notes.py→verify.py в этой папке; читается оригинальный DLL и запускается только статический objdump, ignored full-listing cache не нужен. Игровая или визуальная parity не утверждается.
