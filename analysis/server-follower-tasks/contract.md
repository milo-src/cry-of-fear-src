# Диспетчеры задач сопровождающих NPC

Только статический оригинальный server `hl.dll`, SHA256 `751a68831e4fe3541bbbb24da3c785fb9f6cd3d7e6dcd92125fe1e18f0fce641`. Два primary `10105410` и `101059e0` полностью сверены с сохранёнными C и native ASM. До работы оба блока FUNCTION не имели REVIEW; исходные блоки и хеш каталога закреплены в evidence. `capture.py` воспроизводит bounded objdump и PE reads; `verify.py` проверяет байты/таблицы. Цель не исполнялась. Только два новых REVIEW, остальные C/ASM — support.

Адреса, смещения, маски и task IDs шестнадцатеричные. Все длительности, пороги float, размеры массивов и счётчики явно десятичные. Числовые task IDs здесь важнее заимствованных SDK enum names: имена задач не выдаются за native symbols.

## Общий контракт и границы

Оба entry имеют ECX=this и один stack argument `Task* T`, `RET 4`. `T+0` читается как DWORD task ID, `T+4` — как float argument. NULL this/pev/T не защищены; EAX не нормализован как success, ST0 не является return-контрактом диспетчеров. `101059e0` имеет характер StartTask, `10105410` — RunTask: первый устанавливает deadlines и movement activity либо вызывает однократные действия, второй проверяет завершение и делегирует базовому RunTask. Это вывод из полных тел и прямых вызовов `1000bc60`/`1000b2f0`, а не доказанный concrete virtual slot конкретного spawned класса.

Native MONSTER descriptors `10216e08` подтверждают `+208 m_flFieldOfView`, `+20c m_flWaitFinished`, `+210 m_flMoveWaitFinished`, `+224 m_MonsterState`, `+22c m_iTaskStatus`, `+2d0 m_movementActivity`, `+2dc m_vecLastPosition`, `+304 m_afCapability`. `this+180` — conditions; локальный fail mask=40000000h. Встречающийся EHANDLE `+3e0/+3e4` — отдельный адресат речи, доказанный setter/resolvers; это НЕ `m_hTargetEnt+18c` и НЕ `m_hEnemy+184`. `+3dc` — речевой deadline, `+36c` — счётчик попыток/реплик из предыдущего пакета; исходные имена этих дополнительных полей не заявляются.

Обозначение Complete ниже означает только: если `(conditions+180 & 40000000h)==0`, записать taskStatus+22c=4; иначе сохранить прежний status. Fail означает OR mask40000000h без записи status. Эти диспетчеры не очищают старый fail mask на входе, не продвигают schedule index и не устанавливают универсальный исходный task status. Поэтому отрицательный результат речевого helper не обязательно означает task failure, а наличие старого fail препятствует локальному Complete.

Native `10104f50` возвращает полный EAX0/1 для ordered `(this+3dc)>now`; equality и NaN дают0. Ниже это `Speaking`. `HeadTurn(pointer)` означает `10104e20(this,pointer)`: при capability+304&400h вычисляет vector-by-value target-origin через `100c2760`, один раз корректирует delta yaw на ±360 при выходе за ±180 и вызывает controller helper1000eb70(0,delta); без capability не пишет controller. Прямой1000eb70(0,0.0) в default RunTask не содержит этого внешнего capability gate. Подробности model controller и yaw helper остаются в уже сохранённых animation/navigation контрактах.

Из предыдущего пакета доказаны прямые speech helpers10104110/101041f0/10104540 и native export FollowerUse101048c0. Они не устанавливают concrete vtable этих диспетчеров. Exact LE32 поиск адресов обоих primary по raw `.rdata`/`.data` дал0 совпадений; exact RTTI `.?AVCTalkMonster@@` также не найден. Это ограниченные scans, не доказательство отсутствия runtime класса. Engine API table10222f48 привязана к144 DWORD copy100b4aa0 и eiface header; используются PEntityOfEntIndex, RandomLong, RandomFloat, MakeVectors и AngleVectors. Реализации неизвестных virtual9c/130/1a0/1c8/1d0/240 не подменяются SDK догадками.

## 10105410 — Follower_RunTask

Диспетчер выполнения: case5c сопровождает базовую задачу поворотом головы и репликами; cases60/67/68/69/6b имеют собственные условия ожидания, завершения и ошибки; default сохраняет базовый RunTask.

Native switch: unsigned `(task-5ch)<=0fh`, byte selectors по101057dc, шесть DWORD targets по101057c4. Routes: 5c→101056ca;60→1010564d;67/68→1010543b;69→101055f9;6b→10105560. IDs5d/5e/5f/61/62/63/64/65/66/6a и все значения вне диапазона идут default1010575d. Полная таблица из16 selectors проверяется по raw bytes; signed отрицательный task также попадает в default через unsigned range check.

Case5c: если Speaking и serial-valid speech EHANDLE+3e0, resolver100177a0 даёт private и HeadTurn направляется в его pev.origin+8. После проверки edict отдельного NULL guard private нет. Иначе HeadTurn получает own pev.origin, вызывается greeting10104110 (результат игнорируется), затем RandomLong(0,uint32(this+36c*decimal20)); multiplication реализован LEA/SHL с DWORD wrap, без проверки отрицательного/слишком большого счётчика. При EAX RNG==0 вызывается idle101041f0, даже если предыдущий greeting уже удался. После обеих ветвей всегда `1000b2f0(this,T)`. Если после base RunTask status+22c==4, ещё один HeadTurn(ownOrigin); иначе никакого дополнительного завершения.

Default: при Speaking и serial-valid speech EHANDLE HeadTurn(targetOrigin), затем base `1000b2f0(this,T)` и возврат. Иначе непосредственный `1000eb70(this,controller=0,value=float0)` с отброшенным ST0, затем тот же base RunTask. Здесь нет greeting/idle RNG, нет post-base проверки status==4 и нет дополнительного Complete. Ветвление зависит от speech handle, не target следования.

Case60 использует XY `m_vecLastPosition+2dc/+2e0 - pev.origin+8/+c`. Native вычисляет float32 dy², dx², затем dy²+dx²; переводит сумму в double, берёт SQRTSD и округляет результат обратно в float32. Только ordered отрицательная сумма шла бы в helper1016be90; NaN остаётся на SQRTSD пути. Если ordered distance>T.argument ИЛИ raw movement-goal field+2b8==0: Complete, затем всегда RouteClear100c1a70, даже при старом fail mask. Иначе возврат без изменений. Equality и NaN расстояния сами не завершают задачу при ненулевом+2b8. RouteClear очищает route[0].flags+244 и index+2bc, pev+130, memory+2ec mask20h, field+2b8 и ставит movementActivity+2d0=1; не очищает весь массив маршрута/velocity.

Cases67/68 сначала требуют state+224==1, own virtual9c()==0 и Speaking==0. Любой отказ сразу Fail и return. Затем вызывается engine PEntityOfEntIndex(1), без проверки edict.free/private/player class. При ненулевом edict E вызывается HeadTurn(E+88), то есть его origin при native pev offset80. Case67 после этого проверяет ordered now>m_flWaitFinished+20c, и только тогда Complete. NULL E здесь просто пропускает HeadTurn и всё равно доходит до time gate.

В общем пути67/68 на10105486 ПОСЛЕ возможного HeadTurn заново читается DWORD *T и сравнивается с68h. Следующие обозначения case67/case68 описывают неизменённый task ID; callback может изменить T, поэтому distance/dot ветка выбирается по текущему ID, а не только по исходному switch.

Case68 после возможного HeadTurn разыменовывает E+88/+8c без дополнительного NULL guard: если engine вернулNULL, ветка всё равно пытается читать эти адреса. Вычисляет то же XY расстояние, что выше, между E.origin и own origin; ordered distance>128.0 ставит Fail, но продолжает оставшиеся вычисления. Затем MakeVectors thunk10119320(E+d0) получает адрес E.pev.angles (E+80+50), после чего `101181f0(E+88,ownPev+8,globals+28)` вычисляет XY-normalized direction E→this и его XY dot с vector поglobals+28. ST0 округляется в float32; ordered own m_flFieldOfView+208>dot ставит Fail. Никакой Z компоненты в distance/dot нет. Equality и unordered NaN не ставят эти fail bits. После всех расчётов ordered now>deadline ведёт в Complete, который уже не пишетstatus при установленном fail.

Case69: если own virtual9c()==0, Speaking!=0 и speech EHANDLE serial-valid, HeadTurn(targetOrigin) и return без завершения. Иначе Complete без ожидания m_flWaitFinished и без вызова base RunTask. Private pointer после resolver не защищён повторно. Поэтому это ожидание речи/адресата по локальным gates, а не общий таймер task.argument.

Case6b: PEntityOfEntIndex(1)==NULL сразу Fail. Иначе три DWORD E.origin копируются BY VALUE в12 stack bytes и передаются `100c00f0(this,Vector)`; этот ранее разобранный helper устанавливает ideal_yaw с собственными classname/activity исключениями. Затем current pev.yaw_speed+b0 конвертируется CVTTSS2SI в signed int32 и передаётся own virtual130(integer), его ST0 отбрасывается. Это не float parameter и не масштабирование на frame time в самом диспетчере. Далее HeadTurn(E.origin), и только при ordered now>waitFinished вызывается100bed20(this), чей signed yaw delta округляется ST0→float32. Complete допускается лишь при ordered delta<10.0. ABS не применяется: отрицательная разница любого модуля проходит этот последний gate; equality10.0 и NaN не проходят. Ранее установленный fail mask по-прежнему запрещает status4.

В supporting100bed20 сначала текущий angles.y проходит10117420; exact equality с ideal_yaw даёт ST0=0, иначе10117360(ideal,currentNormalized) формирует signed разницу с одношаговым wrap. Поэтому исправлять условие task6b на abs(delta)<10 было бы изменением исходного поведения. Необычная отрицательная формула самого10117420 уже сохранена в navigation контракте и не заменяется fmod. Ни один локальный RunTask path не принимает return speech/helper за общий success без перечисленных guards.

## 101059e0 — Follower_StartTask

Диспетчер старта: настраивает повороты, отступление и deadlines, вызывает реплики и setter speech handle; часть задач завершается сразу через Complete, часть оставляет status вызывающему scheduler, остальные передаются базовому StartTask.

Native switch: unsigned `(task-50h)<=1bh`,28 byte selectors по10105d9c и14 DWORD targets по10105d64. Полное соответствие:50→10105d45;5e→10105b9c;5f→10105bfe;60→10105beb;61→10105a32;62→10105a0a;63→10105a39;64→10105b47;65→10105b59;66→10105a40;67/68/6b→10105a47;69→10105d5a;6a→10105a66. Остальные51..5d и все вне диапазона→default10105d54. Все addresses/selectors в evidence, включая default routes. Аргумент T не копируется целиком и не валидируется.

Default просто `1000bc60(this,T)`, без собственного Complete. Case50 перед этим очищает speech EHANDLE+3e0 setter10017740(NULL) и всё равно делегирует base StartTask с исходным Task*. Case64 очищает тот же handle, но идёт в локальный Complete, не base. Case69 немедленно возвращается без собственных действий/измененийstatus. Case60 только ставит m_movementActivity+2d0=3 и возвращается, не пишет fail/status/velocity; собственная RunTask60 затем отвечает за условие окончания.

Cases67/68/6b пишут float32 waitFinished+20c = T.argument + currentTime и возвращаются. Никакого clamp отрицательных, infinity или NaN длительностей и собственного Complete здесь нет. Wait таймер связан с соответствующими strict ordered проверками в RunTask; task69 такой deadline не устанавливает.

Case61 вызывает10104ec0(this) и затем Complete. Внутри support helper всегда сначала10104d40 (RandomLong(0,3)+this+370, результат не используется), затем RandomFloat(2.8,3.2) и own virtual1a0(payload=this+374,duration,float1.0,float2.0). Cases62/63/66 вызывают соответственно101041f0 idle,10104110 greeting,10104540 special и затем Complete. Их EAX0/1 игнорируется: если helper отказал без установки conditions fail, task всё равно получаетstatus4. Details речи/target/masks из server-follower-behavior сохраняются, но не повторяются как новые REVIEW.

Case5e сначала own virtual240(0,1), затем заново загружает vtable и RandomFloat(2.0,2.5), округляет duration в float32 и вызывает own virtual1a0(payload=this+390,duration,float1.0,float0.8); затем Complete. Case65 делает то же речевое действие с payload+394 и RandomFloat(2.8,3.2), без предварительного virtual240. Оба native speech вызова имеют ЧЕТЫРЕ stack DWORD. Ghidra ошибочно относит1.0/0.8 к RandomFloat, оставляя два аргумента у callback. Смысл payload/конкретного virtual1a0 и результат фактического воспроизведения не восстанавливаются по этим callsites; return callback игнорируется. Последний float0.8 здесь действительно отличается отfloat2.0 в helper task61.

Case5f строит локальные angles `(pev.angles.x, pev.ideal_yaw+180.0, pev.angles.z)` и вызывает AngleVectors(&angles,&forward,NULL,NULL). Это не простое изменение angles.y entity. После engine callback перечитывает собственный pev, берёт T.argument и покомпонентно float32 формирует candidate=origin+forward*argument. Затем `100c1080(this,activity=3,wait=float2.0,&candidate)`. Supporting wrapper пишет+2d0=3,+2c0=2.0,+2b8=40h, копирует candidate в+2c4..2cc и возвращает EAX от100bddb0. Никакого отката этих записей при нулевом результате нет. При ненулевом EAX сразу Complete; локальный moveWaitFinished+210 при этом не задаётся.

Если100c1080 вернул0, Case5f вызывает own virtual1d0() безstack arguments и округляет ST0 вfloat32. Потом own virtual1c8 получает ровно32 stack bytes: `(Vector ownOrigin BY VALUE, Vector ownViewOfs BY VALUE, DWORD0, float result1d0)`. Восемь DWORD из Ghidra не являются восемью независимыми scalar параметрами: native явно копирует две12-byte структуры; собственный pev загружается отдельно для каждого vector послеcallback1d0. Поля view_ofs+178..180 подтверждены ENTVARS. Нулевой EAX virtual1c8 → Fail иreturn; ненулевой → moveWaitFinished+210=float32(now+2.0), затем Complete. Никакого собственного раскрытия алгоритма cover/pathfinding callback или его гарантии достижения точки этот body не даёт.

Case6a: если speech EHANDLE+3e0 не serial-valid, сразу Complete без изменения yaw. Иначе pev.yaw_speed+b0=60.0, затем resolver100177a0 и targetPrivate.pev безNULLguard; вычисляется target.origin-ownOrigin как Vector BY VALUE для100c2760(this,Vector), ST0 округляетсяfloat32. Для точно нулевого vector этот helper возвращает current angles.y, иначе обращается к engine VecToYaw. Результат helper минус текущий angles.y образует delta. При ordered delta>180.0 вычитается360.0, затем независимо при ordered delta<-180.0 прибавляется360.0: это один проход, не цикл/fmod.

Далее при ordered delta<0 native делает `delta=MINSS(delta+45.0,0.0)`, иначе (включая unordered) `delta=MAXSS(delta-45.0,0.0)`. В pev.ideal_yaw+ac записывается delta+currentYaw, затем Complete. При конечных нормальных числах это оставляет до45 градусов поворота головы и двигает ideal body yaw лишь за пределами этого сектора. При NaN в delta ветка MAXSS берёт свой второй operand0.0; итог равен currentYaw (который сам может бытьNaN). Формула не даёт основания объявлять санитарную обработку всех нечисловых входов. Для helper6a нет собственного вызова virtual130/фактического поворота тела в этом entry.

## Связи расписаний и оставшиеся вопросы

Из предыдущего follower пакета сохранён единственный непосредственно связанный native schedule10219e54: task pointer10219e4c,count=1,interrupt30300h,soundmask0,name `Idle Stop Shooting`, task65h/float0.0. Он назначается ближайшему NPC в10105eb0 и здесь попадает в StartTask65 с payload+394. У этого schedule interrupt включает20000h при soundmask0, поэтому generic ChangeSchedule предупреждает после назначения. Это проверенная связь одной таблицы, не полный inventory всех follower schedules. В самих двух primary нет switch по schedule ID: переключаются именно T.task IDs; выбирать concrete schedule и virtualStart/Run должен внешний scheduler.

Полный generic StartTask1000bc60 и RunTask1000b2f0 находятся в существующем server-monster-scheduler contract; текущий пакет закрепляет их вызовы/возвращаемый контекст, не объявляет их новыми REVIEW. Новая точность: lastPosition+2dc отличается от goal vector+2c4, speech EHANDLE+3e0 отличается от follow target+18c; условия distance используют правильные поля. Конкретные implementations virtual9c/130/1a0/1c8/1d0/240, runtime class factories/vtables для этих entry и полная таблица follower schedules остаются следующими bounded задачами.

Поддерживающий101181f0 нормализует только XY разницу второй точки минус первой, после doubleSQRT округляет длину в float32, вычисляет invLen=float32(1.0/len), затем отдельно умножает DX и DY на invLen в float32 и возвращает ST0 с float32 dot(Yterm+Xterm). Ровно нулевая длина даёт нулевые XY, NaN не считается нулём. Engine MakeVectors thunk10119320 — tail JMP поslot19, AngleVectors slot20; глобальный vector+28 используется caller как направление после этого engine вызова. Детальный engine math не подменяется здесь собственной реализацией.
