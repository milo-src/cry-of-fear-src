# Предварительный расчёт маршрутов оригинального server DLL

Пять новых карточек: `100cbfe0`, `100cfa30`, `100cd550`, `100ca700`,
`100ce920`. Это статический разбор оригинального `hl.dll`, не запуск игры
и не реализация нового поведения. Исходный SHA256:
`751a68831e4fe3541bbbb24da3c785fb9f6cd3d7e6dcd92125fe1e18f0fce641`.
[evidence.json](evidence.json) фиксирует сохранённые C, ограниченные ASM,
сырые константы и вспомогательные документы. [capture.py](capture.py)
воспроизводит ASM и сверяет каждый байт с PE; [verify.py](verify.py)
проверяет уже сохранённые артефакты без повторной дизассемблировки.
Новые импорты REA/Ghidra здесь не выполнялись.

## Навигация и владельцы

| Entry | Предлагаемое имя | ABI и роль |
|---|---|---|
| `100cbfe0` | Graph_BuildCompressedRoutes | ECX=graph, RET; создаёт восемь вариантов таблицы next-hop |
| `100cfa30` | Graph_CheckCachedRouteCosts | ECX=graph, RET; сравнивает стоимости uncached/cached маршрутов |
| `100cd550` | NodeViewer_CollectNodeAndNeighborRoutes | ECX=viewer, один stack node, RET4 |
| `100ca700` | NodeViewer_AppendUniqueUndirectedEdge | ECX=viewer, stack(a,b), RET8 |
| `100ce920` | CTestHull::PathFind | Экспортированный void-метод; входной this не используется, работает с global graph |

У этих методов нет установленного смыслового результата EAX. Псевдокод
не сохраняет все скрытые ECX-параметры; приведённый ABI проверен ASM.

Основная цепь: сохранённый `100ca860` в конце записывает global graph
`102238b0/+0=1`, `+4=1`, `+8=0`, вызывает `100cbfe0`, затем
`100ccba0(mapname)`. Это конкретный подтверждённый caller, не полный
перечень возможных вызовов. Полный разбор создания связей в `100ca860`
остаётся отдельной задачей. `100cbfe0` использует уже описанные
`100cd5e0` (поиск пути) и `100ce830` (декодер next-hop).

| Поле graph | Подтверждённое использование |
|---|---|
| `+0`, `+4` | readiness-флаги, которые проверяет поисковик |
| `+8` | переключатель cached/uncached поиска |
| `+0c` | массив узлов, stride `0x58` |
| `+10` | массив связей, stride `0x18` |
| `+14` | принадлежащий графу byte-pool сжатых строк |
| `+18` | signed число узлов N |
| `+20` | длина byte-pool |
| `node+28+hull*8+mode*4` | смещение строки в byte-pool |
| `node+20`, `node+24` | число исходящих связей и индекс первой |
| `link+4`, `link+14` | target node и float стоимость |

## 100cbfe0: матрица next-hop

Четыре временных выделения происходят до проверки их результатов:
ushort матрица N×N, int путь[N], ushort строка[N], byte scratch[2N].
ASM сначала вычисляет квадрат N через низшие 32 бита IMUL, затем MUL2
с насыщением аргумента до `ffffffff` при unsigned overflow. Переполнение
самого квадрата не проверяется. MUL4 для пути и MUL2 для строки имеют
такое же насыщение, scratch вычисляется обычным ADD N,N без проверки.
Вызовы идут через `1013e5a8→1013e1e9`; последний повторяет allocation
через helper и имеет ветви exception/error. NULL-проверки вызывающего
кода не доказывают, что нехватка памяти обычно возвращает NULL.

Для hull=0..3 и mode=0..1 задаются capability-маски соответственно
`0` и `0x340`. Перед каждым вариантом матрица заполняется `ffff`.
Источники s перебираются по возрастанию, цели d — от N−1 к нулю.
Только неинициализированная ячейка вызывает
`FindPath(path,s,d,hull,caps)`:

* Если count<=1, записываются **две** ячейки: M[s,d]=ushort(s) и
  M[d,s]=ushort(d). Обратная достижимость отдельно не вычисляется.
* Иначе для каждого j<count−1 и каждого k>j записывается
  M[path[j],path[k]]=ushort(path[j+1]). Записи могут перекрывать уже
  заполненные ячейки; отсутствие пути не представлено отдельным тегом.

Сам producer не проверяет readiness, не сбрасывает graph+8 перед
FindPath и не очищает прежний pool. Подтверждённый caller `100ca860`
выбирает uncached заранее. Повторный произвольный вызов producer не
равнозначен чистому пересчёту. Индексы next-hop сужаются до 16 бит,
ограничения N<=65535 и защиты sentinel `ffff` здесь нет. Размер буфера
пути не передаётся поисковику; его self-route пишет два int даже при N=1.

## Кодирование строки и точная граница 0x80

Строка рассматривается в порядке destination=0..N−1. Две формы:

| Серия | Байты | Граница producer |
|---|---|---|
| nextHop[d]==d, последовательные identity-элементы | один byte `-length` | length 1..128 |
| одинаковый nextHop | byte `length-1`, затем signed delta | length 1..127 |

Одиночная identity-серия может объединяться с последующим таким же
next-hop в обычную серию длины 2. Проверка повторения использует
предыдущее значение next-hop и currentCount<127. Identity проверяет
currentCount<128, **до** увеличения, поэтому длина 128 разрешена.
В конце выполняются сброс обычной серии и затем identity-серии.

Для обычной серии выбирается первый представимый signed byte из:
`hop-s`, `N-s+hop`, `hop-N-s`. ASM использует unsigned
`uint32(delta+128)<=255`, диапазон −128..127 включительно.
Если не подходит ни один, тег длины уже записан: код печатает
`Nodes need sorting (%d,%d)!`, **не пишет delta**, не продвигает для
него указатель, продолжает кодирование. Здесь нет сортировки,
отказа операции или rollback. Диагностический счётчик считает два
байта, хотя реально мог быть записан один.

**Несогласованность с native decoder подтверждена с обеих сторон.**
В producer `100cc242..100cc24a` ограничение 128, увеличение
`100cc310`, сброс `100cc328`/`100cc3d2` делает NEG BL.
Серия 128 identity-элементов даёт byte80. В decoder `100ce867`
делает NEG CL, затем `100ce86b` MOVSX ESI,CL: byte80 остаётся
signed −128. Положительный remaining=destination+1 не завершается;
он увеличивается на 128 и читает следующие байты. Это не обычная
identity-серия длины 128. У decoder нет границы длины строки/пула.
Например, допустимая для encoder строка nextHop[d]=d при N=128
сжимается в 80. Это статический пример формата; наличие такой
строки в поставляемых картах и видимое проявление не проверялись.

## Владение pool, повторное использование и завершение

Фактический размер строки — разность указателей scratch, а не
диагностический счётчик. Если graph+14==NULL, размер записывается
в +20, вызывается `10171536(1,size)`, результат публикуется в +14,
передаётся copy-helper10140130; row offset=0.

Если pool уже существует, producer ищет совпадающие байты по всем
смещениям от 0 со **строгим** условием `offset<oldSize-rowSize`.
Последнее возможное смещение пропущено; одинаковая длина pool и row
также не сравнивается. Поиск не требует совпадения с границей ранее
записанной строки. При успехе row offset получает найденное смещение.

При отсутствии совпадения выделяется `10171536(1,oldSize+rowSize)`,
копируется прежний pool, вызывается release-helper101714d1(old),
публикуется новый указатель, добавляется строка; row offset=oldSize,
poolSize+=rowSize. Нет проверки NULL нового pool перед copy,
переполнения сложения и атомарного rollback. Полная реализация
allocation/release и SIMD copy здесь не дореверсена: сохранены
точные call-sites и префиксы двух helpers. Это native функции,
**не** import-thunks. Гарантировать zero-fill/все failure cases нельзя.

`Size of Routes` считает добавленные логические размеры текущего
вызова; это не обязательно итоговый poolSize (прежний pool, dedup,
ошибка delta). Временные ненулевые массивы освобождаются. На любом
достигнутом обычном выходе устанавливается graph+8=1, в том числе
после NULL-проверок, пропустивших расчёт. Это не доказательство
успешной полной таблицы. Деструктор графа/дисковое сохранение —
соседняя область анализа.

## 100cfa30: проверка стоимости, не перестановка узлов

Два массива пути[N] выделяются через ту же ветвь MUL4. При наличии
обоих перебираются hull0..3, modes0/1, все s,d по возрастанию.
Для каждой пары: graph+8=0; FindPath A; graph+8=1; FindPath B.
Если cached count ровно10, проверка пары целиком пропускается.
Это согласуется с лимитом cached path helper, но пропускает также
полный путь ровно из десяти элементов.

Для каждого пути суммируются стоимости соседних **неравных**
индексов. Берётся первая исходящая связь с нужным target и её
float+14. Отсутствующая связь печатает `No link.`, не останавливает
проверку и не добавляет стоимость. Число элементов цикла — integer
count−1; float local_34 в C — переиспользованный stack slot.

ASM точно: обе суммы ADDSS, их разность SUBSS, конверсия нижнего
float в double, очистка знака, COMISD с double0.1 и **JA** в mismatch.
При обычных конечных числах это abs(float(sumA−sumB))>0.1.
Unordered/NaN не проходит JA и не сообщает mismatch (если выполнение
продолжается при floating exceptions); нельзя буквально переносить
C `if (!(abs<=0.1))` для NaN.

Первое расхождение печатает параметры и оба пути, повторяет поиск
с graph+8=0 и затем1 и сразу завершает проверку. Никакого исправления
таблицы или сортировки нет. Сравниваются стоимости, не идентичность
списков/достижимость; два пустых или нулевых по стоимости результата
могут пройти. Прежнее graph+8 не восстанавливается: после любой
обработанной пары оно1, при отсутствии пар/ветви NULL не меняется.

## Viewer: 100cd550 и 100ca700

Viewer хранит destination в +dc, signed count в +e4, два int[128]
массива концов в +e8 и +2e8, hull в +4e8. Append отвергает count>=128,
равные концы и любой уже сохранённый вариант (a,b) или (b,a).
Иначе добавляет исходную ориентацию и увеличивает count. Нет
проверки count>=0 и node ID: отрицательный count проходит guard
и адресует память перед массивами. Нормальная инициализация count=0
подтверждена в supporting viewer Spawn100cf6c0.

Collect вызывает decoder с **ECX=global graph102238b0**, stack
`(node,viewer.destination,viewer.hull,mode0)`, затем Append с
**ECX=viewer**. Повторяет это для target каждой исходящей связи
первоначального node. Здесь нет фильтра доступности link, проверок
readiness/индексов, очистки count, рекурсии или обхода всей цепочки.
В supporting100cf6c0 для N<128 напрямую обрабатываются все узлы;
для N>=128 Collect вызывается для destination, затем для концов
накопленных рёбер до стабилизации count. Поэтому расширение viewer
происходит во внешнем caller, а не внутри Collect.

## 100ce920: фиксированный отладочный путь и сетевой вывод

Экспорт CTestHull::PathFind проверяет globalgraph+0/+4, вызывает
FindPath с **(stack50ints,0,19,hull0,caps0)**. Не выбирает узлы из
позиции this и не перемещает игрока. Нет локальной проверки N>=20,
capacity50 не передаётся поисковику. count0 даёт `No Path!`, неготовый
граф — `Graph not ready!`, иначе печатается `%d\n` с count.

Для каждой соседней пары отправляет MessageBegin(0,23,NULL,NULL),
WriteByte(102), шесть WriteCoord: nodeA.xyz+(0,0,8),
nodeB.xyz+(0,0,8), MessageEnd. Z вычисляется ADDSS с raw float8.
Callback table base10222f48 установлен в supporting100b4aa0;
слоты46/47/48/53 соответствуют Begin/End/Byte/Coord, см.
[engine bridge evidence](../server-client-effects/contract.md).
Pinned SDK называет byte102 `TE_SHOWLINE`, destination0
`MSG_BROADCAST`. Это доказательство отправляемого сообщения,
не визуальная проверка исполнения клиентом.

## Что остаётся открытым

* Создание и перестановка узлов теперь разобраны в [graph builder](../server-graph-builder/contract.md), [ordering](../server-graph-ordering/contract.md) и [entities](../server-graph-entities/contract.md). Перестановка не BFS и не доказывает representability всех signed-byte delta; остальные callers и фактические индексы карт требуют проверки.
* Реальное распределение строк в оригинальных картовых графах:
  наличие identity128, невыразимых delta, лимитов и повреждений.
* Полные контракты CRT helpers10171536/101714d1/10140130 при исключениях,
  allocation failure и overlap; этот пакет фиксирует их использование.
* Вызовы diagnostic100cfa30 и CTestHull::PathFind вне показанных тел;
  экспорт не доказывает игровой сценарий запуска.
* Возможные внешние ограничения размера/валидности графа. Локальное
  отсутствие guard не равно доказанному сбою на поставляемом контенте.
